# 사례 맥락 해설 저장·표시 설계안

상태: 2026-10-23 기존 계층 안에서 구현하고 격리 DB로 검증했다. 운영 DB 마이그레이션·운영 적용·배포는 실행하지 않았다. 기존 DB는 서버의 새 코드 사용 전에 아래 명시적 마이그레이션이 필요하다.

## 목적과 범위

비전공자가 사례의 상황과 수치의 뜻을 이해하도록, 채택된 사례 아래에 쉬운 해설을 기본 표시한다. 해설은 한 번 생성해 DB에 저장하고 같은 입력에는 재사용한다. 개인별 추가 질문은 기존 온톨로지 챗에서 한다. 원문 추출과 원문 기반 사례·사양을 수정하는 기능은 아니다.

기존 계층은 [백엔드 설계](layered_architecture_spec.md), [프론트 설계](frontend_architecture_spec.md)를 따른다. 용어는 [공통 용어](../GLOSSARY.md)를 사용한다.

## 현재 코드에서 확인한 출발점

- `PerspectiveCaseModel`은 사례별 행과 `specifications` JSON을 이미 보유한다. `source_repo.save_perspective_cases()`를 관리자 원문 적용과 `review_repo.save_content()`가 함께 사용한다.
- `concept_service.get_enriched_concept_detail()`이 사례 권한 마스킹 후 `PerspectiveCaseDTO`를 만든다. 위키 화면은 이 DTO를 받는다.
- `SectionPerspectives`의 현재 행 펼침은 원문에서 추출된 `role`, `tradeoff`, `rationale`를 표시한다. 비전공자용 생성 해설이 아니다.
- 기존 `ExplainerAgent.get_explanation()`은 개념 간 관계·용어 해설과 짧은 TTL 캐시를 다룬다. 그 기본 부모·관계·출처 대체값을 새 사례 해설에 재사용하면 안 된다. 재사용 대상은 Agent 클래스와 Gateway 호출 경로다.
- 관리자 `source_service.apply_extractions_to_wiki()`와 검토 승인 API는 위키 변경을 커밋한다. 이 트랜잭션 안에서 새 LLM 호출을 기다리지 않는다.
- 관리자 미리보기와 검토 화면도 `SectionPerspectives`를 재사용하므로 같은 표시 계약이 필요하다.

## 결정한 제품 동작

사례의 원문 설명과 수치 표를 유지하고 그 아래에 `쉽게 이해하기 · AI 해설`을 둔다. 저장된 최신 해설은 클릭 없이 표시한다. 해설의 일반 배경지식은 `용어·배경 설명`으로 구분한다. 원문에 없는 공정 권장값·공차·안전 마진·회사 실적을 생성하지 않는다.

해설은 개별 사례 단위로 저장한다. 최초에는 명시적으로 공개된 사례만 다룬다. 비공개·혼합·공개 여부 미확정 사례의 원래 표시와 권한 신청은 유지하고 공용 생성 해설만 제공하지 않는다. 이번에 비공개 해설의 사용자별 저장·마스킹 체계를 추가하지 않는다.

새 사례를 적용하거나 기존 입력 내용이 바뀌면, 적용 성공 후 별도 DB 세션에서 필요한 해설만 생성한다. 페이지 GET은 저장된 해설만 읽으며 LLM을 호출하지 않는다. 생성 실패·대기·누락은 원문 저장·승인·표시의 실패 사유가 아니다.

## 저장·출력 계약

`perspective_cases`에 nullable `context_explanation` JSON 컬럼 하나를 추가한다. 단일 사례에 최신 공용 해설 하나만 필요하므로 새 테이블·이력 저장소·사용자별 사본은 만들지 않는다. 기존 `specifications`, `role`, `tradeoff`, `rationale`, `evidence_sources`에는 생성 해설을 섞지 않는다.

```json
{
  "basisHash": "생성에 실제 사용한 공개 입력의 서명",
  "generatorVersion": "case-context-v1",
  "generatedAt": "ISO-8601 UTC",
  "content": {
    "explanation": "해당 상황과 수치의 뜻을 쉽게 설명한 문단",
    "background": null
  }
}
```

모델은 `content`의 두 필드만 생성한다. 메타데이터와 서명은 서버가 기록한다. `explanation`은 비어 있지 않은 문자열, `background`는 선택 문자열이다. 고정 문장 수·수치 개수·모든 항목의 해설을 요구하지 않는다. HTML은 받지 않고 화면에서도 텍스트로 표시한다.

응답 DTO는 기존 `PerspectiveCaseDTO`에 선택 필드 `contextExplanation`과 `contextExplanationState`를 추가한다. 표시 상태는 저장 자료와 현재 입력을 비교해 계산하며 DB 작업 상태 테이블을 만들지 않는다.

| 상태 | 화면과 처리 |
|---|---|
| `ready` | 현재 공개 입력과 서명이 일치하는 저장 해설을 표시한다. |
| `missing` | 원래 사례·표를 표시하고 해설은 아직 없다고 알린다. |
| `stale` | 원래 사례·표를 표시하고 이전 해설 본문은 숨긴다. 옛 수치를 최신 내용처럼 보여주지 않는다. |
| `generating` | 해당 프로세스에서 후처리가 예약됐거나 실제 생성 중일 때만 준비 중으로 표시한다. 재시작 뒤 이 상태를 영구 보존하지 않는다. |
| `restricted` | 기존 권한 표시를 유지한다. 공개용 생성 해설 본문은 반환하지 않는다. |

`missing`과 `stale`은 오류나 문서 탈락 판정이 아니다. 요청 중 오류는 Controller의 일시 상태로 처리하며 실패 문구를 성공 해설로 DB에 저장하지 않는다.

## 입력과 재생성 기준

Service 한 곳에서 공개 입력 구성과 서명을 계산한다. 입력은 공개로 확인된 개념의 이름·개요·목적, 대상 사례의 제목·적용 설명·주의사항, 공개 사양의 이름·값·단위·명시 마진·원문 설명과 허용된 근거다. 전체 원문·다른 사례·사용자의 대화·L3 원본을 기본 입력으로 보내지 않는다. 사용한 근거는 기존 원문/등록 출처에서 가져오며 없는 출처를 만들어 넣지 않는다.

`basisHash`는 위 입력의 안정적인 JSON 직렬화로 만든다. 해설 자체·생성 시간·DB updated_at·추출 실행 ID·개념 버전 번호만의 변경은 서명 입력에서 제외한다. 사양의 실제 값·의미·회사/제품/상황·한정어·입력 근거·개념 설명이 바뀌면 재생성 대상이 된다. 모델에 제공하지 않은 정보 때문에 해설을 무효화하지 않는다. 같은 입력을 재적용하면 기존 해설을 재사용한다. 명시적인 해설 방식 변경은 `generatorVersion`으로 구분한다.

조회와 저장 모두 같은 입력 구성 함수를 쓴다. 설명 생성 중 사례가 바뀌면 과거 응답을 저장하지 않는다. 이 검사는 숫자의 정답 판정이 아니라 다른 판본을 덮어쓰지 않기 위한 동시성 검사다.

### 생성 실행과 동시성

관리자 적용·검토 승인 API의 성공 커밋 뒤 FastAPI의 기존 BackgroundTasks 기능으로 변경 개념의 사례를 순차 확인한다. 작업 함수는 요청 DB 세션을 재사용하지 않고 독립 세션으로 필요한 스냅샷을 읽는다. 원문 적용 트랜잭션이 열린 상태나 DB 락을 잡은 상태로 LLM을 기다리지 않는다.

현재 단일 프로세스에서는 사례 ID별 진행 중 요청을 합쳐 자동 생성과 수동 재시도가 겹쳐도 같은 작업을 기다리게 한다. 적용 응답을 보내기 전 Service에 후처리 대상 개념을 표시해 직후 조회에서도 준비 중 상태를 알 수 있게 하고, 완료·실패 시 finally에서 이 표시와 진행 중 요청을 제거한다. 이 표시는 영구 작업 이력이 아니다. 새 큐·Redis 작업 키·상시 Worker·작업 테이블을 만들지 않는다. 각 사례 오류는 그 해설만 실패로 처리하고 다음 사례를 계속 처리한다. 서버가 종료되면 보조 작업은 중단될 수 있으며 원문 적용은 유지된다. 재시작 후 `missing`/`stale` 사례는 권한 있는 관리자의 생성 요청으로 다시 처리한다. 자동 시작·무한 재시도·운영 일괄 재생성은 하지 않는다.

LLM 응답을 받은 뒤 새 세션에서 공개 여부와 입력 서명을 다시 확인한다. Repository의 조건부 UPDATE는 읽은 사례·개념의 기존 `updated_at`을 조건으로 사용해 재확인과 저장 사이의 변경도 방어한다. 다른 저장이나 삭제가 먼저 일어나면 오래된 응답을 버리고 현재 상태를 반환한다. 해설 업데이트 자체로 바뀐 updated_at은 다음 입력 서명에 포함하지 않아 재생성 루프를 만들지 않는다.

다중 Worker 배포까지 한 번의 외부 호출을 보장하지는 않는다. 판본 조건부 저장으로 잘못된 결과 덮어쓰기는 막고, 다른 프로세스의 중복 호출 비용은 현재 범위의 한계로 둔다. 배포 구조가 바뀔 때 분산 실행 조정을 별도로 설계한다.

### 오류와 권한

공용 해설은 사용자의 L3 인가 여부에 따라 입력을 넓히지 않는다. 모든 독자가 볼 수 있는 동일한 공개 입력만 사용한다. 기존 `mask_tier3_perspective(..., False)` 결과가 제한 상태이거나 공개 근거를 확인하지 못한 사례는 공용 생성 대상에서 제외한다. 숫자 토큰화만으로 비공개 문장을 공개화했다고 간주하지 않는다. 공개였던 사례가 비공개로 바뀌면 과거 공개 해설도 반환하지 않는다. 응답·일반 로그에 원문 프롬프트·민감한 모델 응답·인증 정보를 남기지 않는다.

수동 생성은 Level 3 이상으로 제한한다. 일반 독자는 저장 결과를 읽는다. `403`은 권한, `404`는 개념/사례 부재·소속 불일치, `409`는 생성 도중 입력 변경, `502`는 해설 생성 실패로 한정한다. 숫자·단위 문자열 불일치, 문장 수, 특정 정보 누락을 개념·문서·위키 적용의 거절 사유로 추가하지 않는다. 보조 요청이 실패해도 기존 원문은 그대로 보인다.

페이지가 `generating` 상태로 열렸을 때만 Controller가 조회 요청을 제한적으로 재확인하고 완료·실패·화면 이탈 시 멈춘다. 이 조회는 생성 POST를 반복하지 않는다. 생성 완료 알림을 위한 새 SSE·WebSocket을 만들지 않는다. 프로세스 재시작 뒤 `missing`이면 자동 반복 호출 없이 권한 있는 사용자의 재시도로 복구한다.

### 비전공자용 문구

- 섹션 제목 `적응형 실무 사례 및 파라미터 (Adaptive Perspectives & L3 Specs)`는 `적용 사례와 주요 수치`로 바꾼다. API·도메인 식별자는 유지한다.
- 표의 `공정 기준값`은 `원문에 나온 값`으로 바꿔 모든 수치가 권장 레시피인 것처럼 보이지 않게 한다. `물리 안전 마진`은 `허용 오차·안전 여유`, 기존 행의 `해설`은 `원문 설명`으로 바꾼다.
- 단위 null은 `별도 표기 없음`, 마진 null은 `원문에 명시 없음`으로 표시한다. 숫자나 단위를 자동 환산·추정해 채우지 않는다.
- 원문 행에 없는 역할·트레이드오프·근거는 생성 문구로 채우지 않는다. 새 `쉽게 이해하기 · AI 해설`에서 읽기 쉬운 풀이를 제공하고 선택 배경지식은 따로 표시한다.
- 일반 독자의 빈 상태는 짧게 `이 사례의 쉬운 해설은 아직 준비되지 않았습니다`로 알린다. 미리보기에서는 `적용 후 해설이 생성됩니다`로 안내한다. 내부 해시·모델명·API 오류를 제품 흐름에 노출하지 않는다.

## 유지·제외·삭제 범위

원문 추출 프롬프트·수치·귀속 검토, 승인·적용 트랜잭션, 기존 출처와 원문 사례 이력, L3 권한, 챗, 용어 팝오버와 원문 행 설명은 유지한다. 기존 기록을 지우거나 전체 재추출하지 않는다.

사용자에게 노출하는 어려운 영문 중심 제목과 ‘공정 기준값’의 오해 소지가 있는 문구만 교체한다. 원문 `role/tradeoff/rationale`를 생성 해설로 덮는 방식, 페이지 조회마다 생성하는 방식, 실패 시 가짜 해설을 합성하는 방식은 도입하지 않는다. 새 해설을 출처로 재등록하거나 비교·추출의 사실 근거로 되먹임하지 않는다.

## 구현 순서와 검증

먼저 DTO·nullable 컬럼·명시적 마이그레이션과 읽기/서명/조건부 저장을 구현한다. 다음으로 Agent의 작은 생성 메서드와 독립 Service를 추가한다. 이후 두 커밋 성공 경로에 보조 생성 연결, 위키·미리보기의 읽기 응답 확장, 공통 View와 문구 변경을 순서대로 진행한다. 각 단계는 해설이 없어도 기존 위키가 동작하는 상태여야 한다.

검증은 원래 사례 내용을 기준으로 한다. 숫자의 개수나 특정 수치 출력 여부를 합격 조건으로 만들지 않는다. 아래는 구현 시 필요한 대표 시나리오다.

- 첫 공개 사례에 한 번 생성·저장되고 재조회·동일 입력 재적용은 LLM 호출 없이 같은 해설을 반환한다.
- 본문·값·한정어·근거 또는 공개 여부가 바뀌면 이전 해설을 최신처럼 보여주지 않는다. 생성 중 변경·삭제·다른 저장과 경합해도 오래된 응답을 저장하지 않는다.
- 한 사례의 모델 실패·무응답·잘못된 JSON은 다른 사례·원문 적용·승인·표시를 롤백하거나 삭제하지 않는다. 선택 배경 설명 누락은 해설 자체의 실패 사유가 아니다.
- 원문에 수치·마진·역할 설명이 없는 사례도 기존처럼 표시하며 새 필드 부재에 호환된다. 원문 행 설명과 생성 해설이 서로 섞이지 않는다.
- 비공개·혼합·레거시 불명확 사례가 외부 모델 입력·공용 해설·사용자 간 응답으로 새어나가지 않는다. 이미 저장된 공개 해설도 제한 상태 변경 즉시 숨긴다.
- 미리보기의 제안과 저장 사례가 다를 때 옛 해설이 붙지 않는다. 승인 이후에만 생성된다. 생성 없이 미리보기만 열어도 DB·모델 호출이 발생하지 않는다.
- 실제 제품 UI에서 공개 사례의 쉬운 해설 기본 표시, 제한 상태, 권한 있는 재시도, 화면 이동 뒤 늦은 응답 무시, 좁은 화면·키보드 동작을 확인한다. SQLite·PostgreSQL 컬럼 추가와 기존 행 보존을 확인한다.

운영 DB 마이그레이션·기존 전체 자료의 해설 생성·모델 변경·배포는 이 설계 문서 작성에 포함하지 않는다. 사람이 해설을 직접 편집하는 기능과 비공개 전용 해설은 현재 범위에 넣지 않는다.


## 구현·격리 검증 기록 (2026-10-23)

저장 컬럼은 `PerspectiveCaseModel.context_explanation` 하나이며, 기존 DB 변경은 `backend/migrations/add_case_context_explanation.py --database-url <명시한 대상 URL>`로 분리했다. 앱 시작 시 자동 ALTER나 기존 사례 일괄 생성을 하지 않는다. 운영 DB에는 이 명령을 실행하지 않았다.

`scripts/verify_case_context_explanation.py`는 메모리 SQLite와 통제된 모델 응답으로 저장·재사용·한정어 변경·공개 제한·원문 재적용·미리보기 불변·모델 실패·중복 요청·연결 종료·생성 중 변경/삭제·권한·적용 후 예약을 확인한다. 신규 미리보기의 공개 근거가 적용 전 아직 저장되지 않은 경우에만 생성 예정 안내를 허용하며, 내부 근거·근거 미상은 제한 상태를 유지한다. `scripts/verify_case_context_frontend.mjs`는 표시·이스케이프·미리보기·권한 상태·중복 클릭·늦은 응답·오류 보존·유한 GET 재확인을 확인한다. 기존 원문 추출 및 검토 승인 검사도 후처리까지 같은 격리 DB를 사용해 통과했다.

별도 격리 SQLite에서 이전 실제 AMAT·ASML 추출 결과의 22개 개념·7개 사례를 현행 적용 API로 저장한 뒤, 승인된 공개 입력만 기존 Tier 1 Gateway에 보내 7개 해설을 실제 생성·저장했다. 이는 원문을 새로 추출한 검증이 아니다. 최종 코드의 조회·미리보기·동일 생성 요청 재검증에서는 모델 추가 호출 없이 같은 저장 해설을 반환했다. 실제 제품 프론트와 백엔드를 별도 포트에 연결해 공개 페이지와 새로고침 유지도 확인했다.

SQLite 마이그레이션 반복·기존 행 보존·조건부 저장·rollback과 PostgreSQL JSON DDL 생성은 확인했다. 실제 PostgreSQL 서버 연결, 다중 Worker, 장시간 부하, 운영 마이그레이션은 미확인이다. 기존 Vite 빌드는 통과했고 기존 대형 청크 경고는 남아 있다.
