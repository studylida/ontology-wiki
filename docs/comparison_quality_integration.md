현재 호출 흐름은 기존 비교 View → `useComparisonController` → `comparisonService`/`comparisonRepo` → 비교 API → `comparison_service` → 기존 Repository·DTO 순서다. 자료 부족에서 조사로 이동하면 기존 `comparisonContext`를 전달하고 `research_service`가 원래 비교 세션을 다시 조회한다. 선택 자료는 `/comparison-sessions/{id}/research-evidence`로 같은 세션에 보강한다. 비교 또는 조사 후보의 티켓 발행은 출처 스냅샷을 대기 패치로 저장한다. 기존 검토 지시문 → 미리보기·승인의 `materialize()` → `review_repo.save_content()` → 위키·출처 조회 경로를 사용한다.

검증은 제품의 가상환경과 설치된 Vite·React를 재사용했다. 운영 DB와 운영 티켓은 사용하지 않았다. 검증 앱은 `127.0.0.1:8015`에만 바인딩했고 메모리 SQLite와 메모리 캐시를 사용했으며 AI·Crossref 응답은 명시적인 가짜 응답으로 대체했다. UI 로그인은 격리 DB에만 만든 QA 계정으로 했다. 환경 파일·실제 인증 정보는 읽지 않았다.

검증 도구·수정 전후 기준본·적용 패치는 현재 프로젝트의 `.work/comparison-integration/`에 남긴다. `live_app.py`, `verify_live.py`, `verify_frontend.cjs`, `build_frontend.cjs`, `start_live.ps1`로 격리 검증을 재현할 수 있다. 작업 브랜치·기준 스냅샷·최종 커밋 SHA·공유 작업본과 인덱스 보존 결과는 같은 폴더의 `commit.json`에 기록한다. 실제 개선 커밋은 기준 스냅샷 대비 이번 차이만 포함하며, 기준 스냅샷은 통합에 필요한 기존 미커밋 코드의 별도 보존본이다.

실제 외부 모델의 응답 품질·실시간 Crossref 가용성·운영 PostgreSQL·배포 환경은 확인하지 않았다. 운영 서버 재시작·티켓 승인·push·배포는 하지 않았으며, 원문의 등록·수정·삭제도 하지 않았다.
