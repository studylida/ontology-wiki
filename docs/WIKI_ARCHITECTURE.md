## 1. 서비스가 존재하는 이유

**직원이 프로젝트에서 새로 익힌 기술 개념과 고객·업무 경험을 함께 기록하고, 다른 직원이 이를 발전시키며, AI가 유용한 지식의 발견·정리·연결·보강을 돕는 사내 협업형 지식 플랫폼.**

단순 용어 사전도, 업로드한 자료를 기계적으로 요약한 저장소도, AI만 편집하는 자동 위키도 아니다. 나무위키처럼 읽고 직접 수정할 수 있으면서 회사 내부에서 경험한 **실제 활용 목적·고객별 관점·적용 조건**이 축적되어야 한다.

부사장님이 제시한 대표 흐름: 프로젝트에서 모르는 용어 발견 → 사내 Wiki 또는 LLM으로 확인 → 고객 요구사항·활용 내용을 기록 → 작성자·시점 확인 → 동료가 보강·수정 → 과거 버전을 확인. **LLM은 설명·관련 개념 추천·지식 입력을 돕는다.**

## 2. 원본 문헌 · 공용 위키 · 채팅의 역할

- **원본 문헌:** 기술자료·보고서·요구사항 등 출처와 원문을 보존하는 근거. 지금의 업로드·전처리·색인·각주 기능을 유지한다.
- **공용 위키:** 사람과 AI의 도움으로 지속해서 수정되는 **개념 중심 지식**. 같은 개념의 여러 적용 맥락과 문헌을 연결한다. 위키 자체는 장기적으로 여러 프로젝트가 재사용할 데이터 소스다.
- **기존 채팅:** 사용자의 질문에 **위키와 원본 문헌을 함께 검색**해 자연스럽게 답한다. 필요한 근거는 확인할 수 있게 하고 명시적인 위키 작성·수정 요청도 받을 수 있다. 위키를 읽으려면 채팅을 반드시 거쳐야 하는 구조가 아니다.

개인 대화와 공용 위키는 구분한다. 유용한 채팅 답변이라고 해서 자동으로 공용 위키에 올리지 않는다.

## 3. 확정된 제품·운영 원칙

1. **개념 중심, 문서 구조는 유연하게.** 기술 용어·개념을 출발점으로 한다. 실무 활용·고객별 요구·해석 차이·기존 방식의 고려사항·관련 개념은 **실제로 존재하고 도움이 될 때만** 보강한다. 모든 개념에 고정된 목차를 강제하지 않는다.
2. **자유 편집을 기본으로 하고 중요한 문서만 보호한다.** 일반 문서는 직원이 직접 생성·수정하면 관리자 승인 없이 반영된다. 최초 작성자가 독점하지 않는다. **문서의 편집 보호·잠금을 설정하거나 해제하는 권한은 관리자에게만** 둔다. 문서 작성자가 스스로 잠글 수는 없다.
3. **변경 이력과 복구.** 누가 언제 무엇을 바꿨는지, 이전 버전은 무엇이었는지 볼 수 있고 잘못된 편집을 복구할 수 있어야 한다. 다른 직원의 수정을 조용히 덮어쓰면 안 된다.
4. **AI는 먼저 발견하고 제안하지만 무단 공개하지 않는다.** 새 문헌이나 변화에서 기존 개념의 보강점 또는 **새로운 개념**을 발견하면 AI가 수정안/신규 초안을 제안할 수 있다. 직원이 확인·수정·반영한 뒤에만 위키 내용이 된다. 이는 모든 편집에 대한 중앙 관리자 승인과 다르다.
5. **제안 수보다 실질적인 가치.** 모든 새 단어나 기존 설명의 반복을 문서·수정 제안으로 만들지 않는다. 중요한 조건의 누락이나 새로운 적용 사례처럼 실질적인 변화에 집중한다. AI 제안은 무시해도 되며 처리 의무가 없다.
6. **제안 노출은 맥락 중심(C안).** 새 문헌을 올린 직원에게 관련 제안을 알릴 수 있고 다른 직원이 해당 개념을 검색·열람할 때도 자연스럽게 확인할 수 있다. 매일 확인해야 하는 별도 승인·검토 대기열을 주 사용자 경험으로 만들지 않는다.
7. **제안과 핵심 서비스는 독립.** AI의 위키 점검·제안이 실패하거나 확인되지 않아도 원본문헌 색인과 기존 질문·답변은 정상적으로 작동해야 한다.
8. **출처와 해석 범위를 자연스럽게 드러낸다.** 원문에 근거한 설명, 직원의 업무 경험·고객 발언, AI의 해석은 성격이 다르다. 누구의 어떤 자료·상황에서 나온 설명인지 추적 가능하게 한다. 모든 문서에 인위적인 신뢰도 점수나 승인 등급을 강제하지 않는다.
9. **여러 관점의 조건을 지운 채 하나의 정답으로 합치지 않는다.** 고객·회사·시점·사용 목적에 따른 차이를 보존하고 명백한 오류는 고친다. 근거가 불충분한 해석을 공식 입장처럼 확정하지 않는다.
10. **요약의 재인용으로 사실을 증폭시키지 않는다.** 위키 문장과 실제 원문·직원 입력의 연결을 잃지 않는다. 위키와 문헌을 함께 활용하는 채팅도 위키만을 독립 검증의 반복 증거로 취급하지 않는다.
11. **외부 프로젝트는 Markdown을 데이터 소스로 사용한다.** 위키 내부에서 온톨로지 그래프를 억지로 구축하지 않는다. 외부 온톨로지 프로젝트가 Markdown과 안정적인 페이지 식별·판본·출처를 읽고 자신의 목적에 따라 해석한다.
12. **Markdown은 그대로 보존하고 소비 목적별로 다룬다.** 문서 제목·헤더의 문맥은 검색에 유용할 수 있지만 편집 이력이나 장식 정보는 노이즈가 될 수 있다. 원문을 파괴하거나 무조건 헤더를 지우지 않고 검색·LLM 전달에 적합한 표현을 파생한다. 구체적 알고리즘은 나중에 결정한다.
13. **개발 단계의 모든 위키 지식은 하나의 공용 공간에서 다룬다.** 구현·실사용 검증의 편의를 위해 직원이 올린 지식을 고객사·프로젝트·부서·내용 유형에 따라 나누거나 별도 열람·등록 승인 절차를 두지 않는다. 로그인한 직원은 공용 위키를 모두 열람한다. 나중에 실제 필요가 생기면 **공통 인증·인가 경계에서 접근 권한을 검사하도록** 확장한다. 현재 이 결정을 이유로 복잡한 ACL·지식 분류·등록 제한 UI를 미리 만들지 않는다. 이는 개발 편의상 단순화한 정책이지 실제 기밀자료의 외부 공개나 운영 환경의 무제한 접근 허용을 결정한 것은 아니다.

14. **AI 편집은 최소 변경을 기본으로 한다.** 기존 위키의 내용과 표현·문서 구조·직원의 기여를 최대한 보존하고 새 근거로 확인된 조건·사례·연결 등 **실제로 필요한 부분만** 수정·추가·정정하도록 제안한다. 전체 문서 재작성이나 불필요한 문체 통일을 기본 동작으로 삼지 않는다. 직원은 기존 내용과 제안된 변경의 차이를 확인하고 수정하거나 적용할 수 있다. 문서 전체의 재구성이 정말 필요한 경우에는 이유를 설명하고 별도로 선택하게 한다.

## 4. 대표 사용자 경험

- **알아보기:** 직원이 프로젝트에서 낯선 용어를 만났을 때 기존 위키로 의미·맥락·관련 개념을 살펴보고 더 궁금하면 채팅에 질문한다.
- **쌓아가기:** 미팅에서 들은 활용 조건을 직접 기록하거나 AI에게 정리를 요청한다. 직접 편집은 즉시 저장되고 AI는 기존 내용을 최대한 보존한 부분 변경안을 제안한다. 직원은 변경 전후를 확인하고 수정하거나 반영한다.
- **발전시키기:** 새 자료가 들어오면 AI가 누락된 중요한 설명·새로운 사례·새 개념을 제안한다. 업로드 시점이나 관련 위키를 읽는 시점에 자연스럽게 확인할 수 있다.
- **함께 고치기:** 다른 직원이 내용을 수정·보강하고 버전별 변경 내용을 살펴보며 필요하면 되돌린다.
- **재사용하기:** 다른 온톨로지 프로젝트가 같은 위키의 Markdown을 판본·출처와 함께 데이터 소스로 사용한다.

### 4.1 자유로운 탐색과 문맥에 맞는 하이퍼링크

**사용자에게 지정된 탐색 시작점·학습 순서·관계 지도를 강요하지 않는다.** 문서를 읽다가 자연스럽게 등장하는 중요 개념에서 필요한 만큼만 다음 문서로 이동할 수 있도록 한다. 관련 개념 목록은 본문 연결의 **보조 수단**이다. 링크 수를 늘리는 것 자체가 목표가 아니며, **링크가 없는 것은 실패가 아니다.** 의미 없는 단어마다 링크를 추가하여 가독성을 떨어뜨리는 slop을 피한다.

- 본문에 등장한 중요한 기술 개념, 비교 대상, 상·하위 개념 등은 **실제로 해당 개념을 지칭하는 맥락에서만** 링크 후보가 될 수 있다. 개념 간 관계 유형을 억지로 부여하거나 별도 온톨로지 관계를 추출·저장할 필요는 없다.
- 같은 이름·약어가 서로 다른 의미를 가질 수 있다. 문서가 다루는 의미와 구별해야 할 다른 개념이 실제로 존재한다면 **문서 상단에서 '다른 의미를 찾고 있나요?'** 같은 짧은 안내로 잘못된 탐색을 줄인다. 동의어·별칭은 같은 개념으로 취급할 수 있지만 동음이의어는 함부로 하나로 합치지 않는다.
- 링크 대상 페이지가 없거나 의미가 모호하다면 무리하게 링크하거나 빈약한 새 문서를 자동 생성하지 않는다. 직원은 필요할 때 직접 새 개념·링크를 추가하거나 AI 편집 보조를 사용할 수 있다.

### 4.2 AI 보조 링크 제안 — 의미 확인과 최소 수정

**위키에 저장된 Markdown 자체에 하이퍼링크를 반영**한다. 읽을 때마다 별도 AI가 링크를 새로 계산하여 화면에만 보여주는 구조를 기본으로 삼지 않는다. 문서 작성·수정/보강 과정의 기존 AI 편집 보조가 링크도 함께 제안한다. 직원이 직접 넣는 링크는 일반 자유 편집으로 처리한다.

AI가 링크를 제안할 때에는 다음 네 판단을 구분한다.

1. **후보 검색:** 본문에 등장한 표현과 기존 위키의 제목·별칭·동의어를 키워드 검색과 벡터 유사도 등으로 대조해 가능성 있는 연결 대상을 찾는다. **검색으로 후보가 나왔다는 사실은 같은 개념이라는 보증이 아니다.**
2. **AI 문맥 검증:** 현재 문장·문단의 표현이 **그 대상 위키와 정말 동일한 개념을 지칭하는지** 확인한다. 이름만 같거나 단순히 의미가 비슷한 경우를 구별하고 애매하면 링크 제안에서 제외한다.
3. **중요도·가독성 검토:** 동일 개념임이 확인되어도 독자의 이해와 다음 탐색에 실제로 유용한 핵심 표현에만 선별해 제안한다. 동일 용어의 반복 출현마다 모두 연결하거나 이미 충분히 연결된 본문에 링크를 더하지 않는다.
4. **직원 확인 후 Markdown에 저장:** 기존 문장·형식·직원의 기여를 최대한 보존하고 **필요한 표현만 하이퍼링크로 바꾸는 국소 수정안**을 보여준다. 직원이 변경 전후를 확인·수정·적용하면 새 위키 판본으로 보존한다. AI가 임의로 확정하지 않는다.

**의사결정의 비대칭:** 연결을 놓쳐도 무방하지만 **잘못 연결하면 독자와 외부 지식 소비자를 오도한다.** 따라서 보수적인 판단을 우선한다. 벡터 점수·AI 확신도만으로 의미 동일성이 보장된다고 주장하지 않으며 실제 평가를 통해 오류를 확인한다.

링크 검토는 신규 독립 에이전트나 상시 실시간 LLM 호출 기능이 아니라 **기존에 합의한 위키 편집 제안의 일부**다. 외부 온톨로지 프로젝트는 직원이 적용한 뒤 실제 Markdown에 기록된 링크를 읽을 수 있다.

### 4.3 새 문서 작성 시 중복·유사 개념 안내

직원 또는 AI가 신규 개념 문서를 작성하려 할 때 **이미 비슷한 위키가 있는지 먼저 알려준다.** 제목과 본문을 참고하여 키워드 검색과 의미 검색을 결합하고 재순위화하는 방식을 후보로 삼는다. 이 또한 **동일한 개념인지 단순히 관련 있는 문서인지** 구분해야 한다.

- 비슷한 기존 문서를 보여주고 **기존 문서 보강**과 **새 문서 작성 계속하기** 중 직원이 결정하도록 한다.
- 유사 결과만으로 생성을 강제로 차단하거나 중복 문서라고 자동 확정·병합하지 않는다.
- AI의 **신규 개념 초안 제안**에도 같은 중복 안내 취지를 적용해 불필요하게 얕은 문서가 쌓이지 않게 한다.

검색 조합·재순위화 모델·점수·임계값·호출 비용·구현 시점·예외 기준은 **아직 확정한 기술 명세가 아니다.** 향후 실제 위키 데이터와 오연결/중복 안내의 유용성으로 평가한다.

## 8. 구현 인계 전 검토 보완 — 최소 연결 규칙

> **2026-10-29 설계 검토 결과:** 제품 방향을 다시 설계하지 않는다. 아래는 이미 합의한 자유 편집·직원 확인·출처 보존·기능 독립성이 실제 사용자 흐름에서도 지켜지도록 하는 최소 요건이다. 테이블·API 필드·동시 편집 알고리즘은 구현자가 정한다. 현재 코드에 취약점이 입증됐다는 보안 감사 결과는 아니다.

### 8.1 편집 권한과 직원의 변경 보존

일반 위키는 작성자가 아니어도 직원이 편집한다. 기존 **업로드 문헌의 등록자/관리자 수정 규칙을 위키에 그대로 복사하지 않는다.** 보호 문서에서는 일반 직원의 제안은 가능하되 본문 반영은 관리자만 한다. 직접 저장·AI 제안 적용·과거 버전 복구 모두 같은 현재 권한 검사를 서버에서 수행한다. AI의 판단이나 화면 버튼 숨김으로 이를 대신하지 않는다.

AI가 읽은 뒤 직원이 먼저 수정했거나 문서가 잠겼다면 오래된 수정안을 조용히 적용하지 않는다. 최신 내용과 다시 비교하도록 안내하고 입력과 제안은 잃지 않는다. 같은 적용 요청의 재전송은 변경을 중복 반영하지 않는다. 복구는 과거 이력을 삭제하는 대신 복구 사실을 남긴 새 판본으로 만든다. 자동 병합 엔진이나 복잡한 공동 편집기는 요구하지 않는다.

### 8.2 미반영 초안과 공개 지식의 구분

AI 제안은 검토 화면에서 초안으로 보여줄 수 있지만 **적용되기 전에는 일반 위키 본문·답변 근거 검색·외부 지식 내보내기의 공개 지식에 포함하지 않는다.** 직원의 일반 직접 편집은 저장 즉시 반영한다. 중앙 관리자 승인 절차는 만들지 않는다.

위키 저장과 검색 색인 준비는 구분한다. 색인 실패가 편집 내용을 지우거나 위키 열람을 막으면 안 된다. 검색 준비 상태와 재시도 가능 여부를 알리고 낡은 색인 내용을 새 판본으로 표시하지 않는다. 같은 개념의 판본이 둘 이상 현재 근거로 중복 활성화되지 않게 한다. 문서 제목 변경 후에도 내부 링크와 과거 판본 인용은 같은 페이지를 가리켜야 한다.

### 8.3 출처·공개 범위·기존 채팅의 연결

위키의 설명을 인용했다면 실제 위키 판본을 가리키고 원문을 읽었다면 실제 원문 구간을 가리킨다. 위키와 그 바탕 문헌을 독립 검증 근거 두 개로 부풀리지 않는다. 직원 경험은 작성자와 업무 맥락으로 남길 수 있으며 파일 출처가 없다고 등록을 막거나 가짜 원문 인용을 만들지 않는다.

개인 대화에서 위키 반영을 요청하면 **공용으로 저장될 내용과 필요한 근거만 미리 보여주고** 직원이 반영한다. 전체 개인 대화나 다른 직원의 대화를 공용으로 공개하지 않는다. 외부 Markdown 조회는 기존 인증 경계를 사용하며 사내 공용이라는 이유로 익명 공개하지 않는다. 위키·원문 모두 실제 판본과 접근 상태를 답변·원문 조회·대화 복원에 일관되게 적용한다. 기존 채팅의 개인 소유권과 인용·철회 검사를 우회하는 연결은 만들지 않는다.

### 8.4 저장형 링크와 안전한 표시

직원이 넣은 링크와 AI가 제안한 링크는 같은 안전한 Markdown 표시 경로를 사용한다. 기존 렌더러를 재사용하되 필요한 내부 위키 링크만 허용하고 임의 스크립트·실행 가능한 HTML·위험한 URL을 허용하는 식으로 완화하지 않는다. 문헌과 위키의 텍스트는 참조 자료이지 사용자 권한이나 공개 결정을 바꾸는 실행 지시가 아니다. 원본 Markdown 반환과 HTML 화면 렌더링은 구분한다.

### 8.5 능동적 제안과 독립적인 기본 흐름

신규 문헌이나 새 판본의 사용 가능한 내용이 준비된 뒤 관련 위키의 개선안을 만드는 실제 자동 연결을 제공한다. 자동 감지는 우선 **서비스에 들어온 자료와 판본 변경**을 뜻하며 외부 웹 감시를 추가하지 않는다. 위키 제안 실패나 보류는 문헌 검색 가능 상태·직원의 편집·채팅 완료를 되돌리거나 막지 않는다.

같은 입력에 대한 반복 작업과 제안 적용이 다시 무한한 제안을 낳는 순환을 막는다. 합리적인 작업량·호출 한도를 두고 같은 변경에는 중복 제안을 쌓지 않는다. 읽기·새로고침은 생성 호출을 일으키지 않는다. 필요할 때의 작은 안내 → 변경 부분과 이유/근거 확인 → 수정·적용 또는 무시로 시작하며 상세 만료 정책·알림 센터·대량 관리 화면은 요구하지 않는다.

### 8.6 검토 후 이번 구현에 추가하지 않는 것

부서별 ACL, 관리자 승인 대기열, 자동 문서 병합·분할, 완벽한 이름 분류 체계, 복잡한 제안 만료 정책, 실시간 공동 편집, 그래프 DB, 별도 자동 심판, 평가 대시보드, 신규 다중 에이전트 플랫폼은 핵심 흐름의 선행 조건이 아니다. 모델·임계값·화면 배치 같은 상세는 기존 원칙을 해치지 않는 단순한 방식으로 구현하고 실사용으로 보완한다.


## 9. 구현 상태 — 직원 직접 편집 1단계 (2026-10-29)

현재 구현 범위는 **일반 직원의 페이지 작성·제목 검색·열람·직접 편집·판본 이력·변경 비교·복구** 및 **관리자의 보호·해제**다. 기존 채팅·문헌의 정책은 그대로 두고 위키는 독립 모듈로 연결한다. 새 위키의 모든 미래 기능이 구현됐다는 의미가 아니다.

페이지 식별자는 제목과 독립이고 동일 제목의 개념도 만들 수 있다. 내용 판본은 보존하며 복구는 새 판본이다. 편집 기준에는 보호 상태 변경도 포함해 편집 도중 잠금·해제나 동료의 변경이 있었다면 다시 비교하게 한다. 직접 저장·복구·보호는 현재 서버 권한과 같은 동시성 경계를 사용한다. 같은 저장 요청의 재전송은 한 번 반영된 결과를 확인할 뿐 다시 쓰지 않는다.

직원 경험이나 알려진 문헌은 선택적인 근거·업무 맥락 메모로 기록한다. 파일 근거가 없다고 저장을 막지 않으며 메모를 자동 검증한 인용으로 취급하지 않는다. 사용자 입력과 원문 Markdown은 보존하고 표시할 때 기존 안전한 렌더러를 재사용한다.

기존 migration은 변경하지 않고 `004_shared_wiki.sql`을 추가한다. 위키 수동 편집 자체는 모델·worker 없이 작동한다. 실제 API 계약·실행법은 README의 **공용 위키 1단계** 절에 유지한다. 아직 전송하지 않은 초안은 메모리에 보존하고 이탈을 경고한다. 이미 전송한 저장 요청은 사용자별 sessionStorage에 요청 ID·본문과 확인된 저장 결과만 보존하여 같은 탭의 새로고침 뒤 명시적으로 이어받는다. 조회 실패가 확인된 저장 결과를 지우지 않으며 저장 성공이 확인됐다면 다시 쓰지 않고 조회만 재시도한다. 로그아웃 시 해당 복구 상태도 지운다. 일반적인 초안 자동 저장 기능이나 브라우저 종료 이후 복구는 제공하지 않는다.

의미 검색·새 문서 유사도 안내·문맥상 링크 제안·AI 초안·능동적 보강·위키/원문 결합 RAG·외부 전용 Markdown API는 **다음 단계**다. 기존 채팅·RAG의 구현이나 문헌 데이터는 이번 위키 추가로 초기화하지 않는다.

### 9.1 2단계 진입 전 경계 정리

- 직원·관리자 주체 판정은 `identity/authorization.py`에서 재사용한다. 위키의 열람·편집·보호 및 현재 판본 검사는 `wiki/policy.py`가 소유하고 API 응답의 `canEdit`/`canProtect`도 같은 판정에서 만든다. Documents의 등록자별 관리 정책과 혼동하지 않는다.
- Controller는 HTTP와 화면 수명주기를, Service는 쓰기·복원/확인 흐름을, Repository는 DB·HTTP·세션 I/O를 담당한다. Entity/DTO는 기존 1단계 계약을 유지한다. 새 모델·검색 기능이나 빈 전달 계층을 추가하지 않는다.
- 복구·잠금에서 충돌해도 편집 양식 밖에서 최신 상태를 확인하고 명시적으로 작업을 다시 선택할 수 있다. 지연된 이전 문서 조회는 새로 선택한 문서의 화면이나 오류를 덮어쓰지 않는다.
- 원격의 `004_shared_wiki.sql`과 현재 API를 유일한 1단계 기반으로 유지한다. 별도 로컬 실험의 `004_wiki.sql`이나 다른 계약을 함께 적용하지 않는다. 2단계는 현재 문서·판본·권한 계약을 재사용해 탐색과 색인을 추가하며 기존 데이터를 초기화하지 않는다.
