# 데이터 이전과 구형 실행 코드 제거

이 문서는 기준 커밋 `8e7fb58bd0c051fff99ab97a39278ef2bdc5ba0a`의 자산을 새 대화 중심 서비스로 옮길 때의 보존 기준, 현재 구현한 명령, 실제 검증 범위와 남은 작업을 설명합니다. 현재 작업은 별도 브랜치와 개발 DB에서 수행했습니다. **실제 운영 DB·전체 원문 저장소·운영 계정 및 권한 내역은 제공되지 않았고 접근하지 않았습니다. 운영 데이터 이전, 트래픽 전환, 배포는 수행하지 않았습니다.**

기존 코드의 유지 여부와 데이터의 보존 여부는 별도로 판단합니다. 새 서버는 `backend/knowledge/`를 실행하며, 기존 위키·비교 탭과 플로팅 챗봇의 서버를 호환 계층으로 함께 운영하지 않습니다. 이전 시스템의 데이터가 새 스키마에 맞지 않더라도 원본과 수정·검토 이력을 먼저 보존합니다.

## 1. 현재 구현된 범위

| 작업 | 현재 동작 | 의미하지 않는 것 |
| --- | --- | --- |
| 새 스키마 설치·갱신 | `knowledge.cli migrate`가 버전별 SQL과 적용 해시를 기록합니다. | 기존 운영 스키마의 자동 변환이나 운영 배포가 아닙니다. |
| 레거시 내보내기 검사 | `import-legacy` 기본값은 읽기 전용 dry run입니다. 원본 파일을 읽고 구조·ID·숫자 형식을 검사합니다. | 원문 파일의 실재, 외래키 정합성, 기존 권한의 정확성까지 검증하지는 않습니다. |
| 레거시 원본 보관 | `--apply`일 때 원본 export 바이트, 반입 명세, 각 행의 원래 값과 ID, 매핑 대기 상태를 보존합니다. | 현재 문헌·개념·관계·대화 테이블로 자동 게시하지 않습니다. |
| 고정 평가 자료 반입 | 명시적인 개발용 승인과 고정 입력 해시를 확인하여 문헌·구간·기존 임베딩 캐시를 개발 DB에 반입합니다. | 운영 문헌 승인, 출처 진위 인증, 전문가 정답 검증이 아닙니다. |
| 구형 실행 코드 제거 | 기존 API·서비스·탭 전용 검증 스크립트를 제거하고 과거 설계 문서를 `docs/legacy/`에 보관합니다. | JSON, 원문, 과거 지식·검토 데이터까지 폐기한다는 뜻이 아닙니다. |

현재 `import-legacy`는 **보존과 전환 대기 상태를 만드는 도구**입니다. 실제 운영 자료의 테이블·분류·소유자·출처를 확인한 뒤 활성 도메인으로 옮기는 매핑 작업은 아직 실행하지 않았습니다. 이 작업이 끝나기 전 `preserved_pending_mapping`을 이전 완료 상태로 표현하지 않습니다.

## 2. 새 스키마와 마이그레이션

관련 구현은 `backend/knowledge/migration/schema.py`, `backend/migrations/v2/`입니다. 아래 명령은 저장소의 `backend/`에서 가상환경을 활성화하고, 검증용 환경변수를 이미 설정한 상태를 가정합니다. 비밀번호나 API 키를 명령 기록에 넣지 않습니다.

```bash
python -m knowledge.cli migrate --database-name ontology_wiki_dev
```

`--database-name`은 설정된 `OW_DATABASE_URL`의 DB명과 일치해야 합니다. 불일치 시 연결 전에 중단합니다. 이 검사는 잘못된 DB명을 줄이는 장치이며, 같은 이름의 다른 서버를 구분하는 인증 장치는 아닙니다. 실행자는 비밀번호를 표시하지 않는 방법으로 호스트·포트·DB명·계정의 실제 대상을 확인해야 합니다. 현재 개발 대상은 격리된 로컬 `127.0.0.1:55432/ontology_wiki_dev`입니다.

마이그레이션은 트랜잭션 안에서 advisory lock을 얻고, `knowledge_schema_migrations`의 버전과 SHA-256을 대조합니다. 같은 SQL은 재적용하지 않고, 이미 적용된 파일이 바뀌면 중단합니다.

| 파일 | 역할 |
| --- | --- |
| `001_initial.sql` | 새 제품의 초기 스키마입니다. 적용 후 수정하지 않습니다. |
| `002_legacy_imports.sql` | 원본 export 명세를 보존하는 `legacy_imports`와 `legacy_archive.first_import_id`를 추가합니다. 기존 archive 행은 그대로 남으며, 반입 원본을 확인하지 못한 과거 행의 연결은 `NULL`로 둡니다. |

스키마 변경은 다음 번호의 SQL로 추가합니다. 현재 실행기는 함수 본문이 없는 단순 DDL을 세미콜론으로 나누어 실행합니다. 향후 함수·트리거처럼 본문 안에 세미콜론이 필요한 변경을 추가한다면 실행기를 먼저 보완해야 합니다. 이를 범용 SQL 파서로 간주하지 않습니다.

## 3. 레거시 export 보존 계약

### 3.1 입력 형식과 검사

UTF-8 JSON(선택적 BOM 포함)의 루트에 `tables` 객체가 필요합니다. 테이블 이름 아래에는 각기 원래 `id`를 가진 행의 배열을 넣습니다. 다음은 형식 예시이며 실제 운영 스키마의 목록이 아닙니다.

```json
{
  "exportedAt": "2026-10-26T00:00:00Z",
  "tables": {
    "sources": [{"id": "source-1", "visibility": "private"}],
    "concepts": [{"id": 17, "name": "예시 개념"}],
    "review_tickets": [{"id": "review-1", "status": "legacy-status"}]
  }
}
```

입력 테이블 이름을 현재 모델 이름으로 먼저 바꾸거나, 이전에 쓰던 상태 문자열을 새 승인 상태로 치환하지 않습니다. `tables` 바깥의 export 시각·버전 같은 메타데이터는 원본 파일에 그대로 남습니다. 각 행은 별도 JSONB 보관 레코드가 됩니다.

검사 규칙은 다음과 같습니다.

- `source-system`은 비어 있지 않은 160자 이하 문자열입니다. 원래 시스템과 데이터 인스턴스를 식별하는 고정 이름을 사용합니다.
- 테이블 이름도 비어 있지 않은 160자 이하 문자열이어야 합니다.
- 행 ID는 비어 있지 않은 문자열 또는 정수입니다. `null`, 빈 문자열, 공백만 있는 문자열, 객체, 배열, 불리언, 소수는 거절합니다. 새 ID를 추측해서 채우지 않습니다.
- 같은 테이블의 중복 ID, 중복 JSON 객체 키, `NaN`·`Infinity`, JSONB가 보존할 수 없는 NUL 문자를 거절합니다. 숫자 ID `1`과 문자열 ID `"1"`은 매핑 키에서 충돌하므로 같은 테이블에 함께 넣을 수 없습니다.
- 서로 다른 테이블 또는 서로 다른 `source-system`의 같은 ID는 별개로 보존합니다.

기존 데이터에 ID가 없는 연결 테이블이 있다면 export 단계에서 원래 복합키를 손실 없이 식별하는 규칙을 정하고 그 규칙과 구성 필드를 함께 기록해야 합니다. 현재 도구가 행 순서나 내용을 보고 임의 ID를 만들어 주지는 않습니다.

### 3.2 읽기 전용 검사와 적용

```bash
python -m knowledge.cli import-legacy --export /path/to/legacy-export.json --source-system ontology-wiki-legacy
```

기본값은 `dry_run`입니다. DB 세션을 열지 않고 원본 보관 디렉터리를 만들거나 파일을 쓰지 않습니다. 테이블별 행 수, 전체 행 수, export SHA-256을 반환하며 `importId`와 `rawPath`는 `null`, `sharedSearchImported`는 `false`입니다. 이 결과는 입력 구조 검사이며 DB의 저장 한계나 모든 업무 정합성 검사의 통과를 뜻하지 않습니다.

다음 명령은 **확인한 별도 개발 환경에서만** 보관을 적용하는 예시입니다.

```bash
python -m knowledge.cli import-legacy --export /path/to/legacy-export.json --source-system ontology-wiki-legacy --apply
```

`import-legacy` 자체에는 `--database-name` 인자가 없습니다. 적용 전 `OW_DATABASE_URL`의 실제 대상과 `OW_STORAGE_PATH`를 확인해야 하며, 앞선 다른 명령의 확인 결과가 이후 바뀐 환경설정까지 보장한다고 가정하지 않습니다.

적용 시 아래 자산을 함께 보존합니다.

| 저장 위치 | 보존 내용 | 식별·중복 처리 |
| --- | --- | --- |
| `OW_STORAGE_PATH` 아래 content-addressed 원본 파일 | 공백, 숫자 표기, 키 순서, BOM 등을 포함한 export 전체 바이트 | SHA-256으로 저장 경로를 정하고 기존 파일의 해시를 재확인합니다. |
| `legacy_imports` | source system, export 해시, 원본 상대 경로, 테이블별 행 수, 전체 행 수, 반입 시각 | `(source_system, export_sha256)`당 하나입니다. |
| `legacy_archive` | 원래 테이블·ID, 각 행의 JSONB 값, 행 해시, 최초 반입 명세, 분류 | `(source_system, source_table, source_id, record_hash)`당 하나입니다. |
| `legacy_mappings` | 원래 ID와 새 대상의 연결 자리 | `(source_system, source_table, source_id)`당 하나이며 처음에는 대상이 없고 `preserved_pending_mapping`입니다. |

원본 파일을 저장한 뒤, 명세·행·매핑은 하나의 짧은 DB 트랜잭션으로 커밋합니다. DB 저장 중 실패하면 이 세 테이블의 변경을 함께 롤백합니다. 파일 저장과 DB 커밋은 분산 트랜잭션이 아니므로 **DB 실패 후 참조되지 않은 원본 파일이 남을 수 있습니다.** 이 경우 실패 내역을 기록하고 재실행할 수 있습니다. 공유 원본일 수 있는 파일을 오류 처리 중 임의로 삭제하지 않습니다. 정리가 필요하면 DB 참조와 파일 해시를 대조한 별도 보존 정책에 따라 수행합니다.

### 3.3 정밀도, 반복 반입과 판본

소수는 `Decimal`로 파싱한 뒤 숫자로 직렬화하여 PostgreSQL JSONB에 전달합니다. 예를 들어 정밀한 측정값을 Python `float`로 반올림하거나 문자열로 바꾸어 저장하지 않습니다. PostgreSQL이 지원하는 숫자 범위 밖의 값은 DB 적용 오류가 날 수 있으며, 이 경우 행 일부만 커밋하지 않습니다.

JSONB는 공백·키 순서·숫자의 원래 표기 형태를 보장하는 원본 형식이 아닙니다. 바이트 단위 증빙은 보존한 export 파일과 `export_sha256`으로 확인합니다. 일반 JSON 디코더나 ORM으로 읽은 숫자는 소비자 설정에 따라 다시 부동소수점이 될 수 있으므로, 정밀도 감사에는 원본 바이트 또는 PostgreSQL의 `payload->>'필드'` 텍스트 추출을 사용합니다. 보관 JSONB를 일반 `float` 기반 코드로 읽어 재수출한 결과를 원본과 동일하다고 표시하지 않습니다.

반복 반입은 다음과 같이 동작합니다.

- 같은 export를 다시 반입하면 명세·동일 행·매핑이 중복 생성되지 않습니다.
- JSON 객체 키 순서만 달라진 export는 원본 바이트가 달라 별도 명세를 갖지만 동일 행은 재사용합니다. 모든 숫자 표기까지 의미적으로 동일하게 정규화한다고 가정하지 않습니다.
- 같은 원래 ID의 내용이 수정되면 새 행 해시로 추가 보관합니다. 이전 전문가 수정 내용을 덮어쓰지 않습니다.
- 다음 export에서 사라진 행을 보관소에서 자동 삭제하지 않습니다. 삭제·철회 여부는 원래 시스템의 이력과 별도로 대조합니다.
- 기존 매핑의 대상과 disposition을 반복 반입으로 덮어쓰지 않습니다.
- `first_import_id`는 해당 행을 처음 보관한 export를 가리킵니다. 이후 모든 export의 포함 관계를 표현하는 별도 이력 테이블은 아닙니다. 특정 시점의 전체 내용은 그 export 원본으로 확인합니다.

### 3.4 보관 범위와 접근 경계

`restricted_legacy_archive`는 현재 보관 데이터의 분류값입니다. 이 값만으로 DB 암호화나 행 수준 보안이 자동 구성되는 것은 아닙니다. 현재 일반 문헌·검색 API와 RAG 저장소는 archive 테이블을 조회하지 않으며, 반입 과정은 문헌 승인·색인·개념·관계·작업 생성을 하지 않습니다. 원본 보관 디렉터리와 DB 직접 접근 권한, 백업 접근 권한도 제한해야 합니다.

export 안의 `raw_path`가 가리키는 PDF·HTML·이미지 등 **별도 원문 파일은 이 명령만으로 복사되지 않습니다.** export 자체의 보존과 원문 파일 모음의 보존을 각각 확인해야 합니다. 경로가 남아 있다는 이유만으로 파일 내용까지 확보했다고 표시하지 않습니다.

## 4. 반드시 보존하고 대조할 데이터

실제 운영 export를 받으면 다음 표를 그 스키마와 대조하여 이전 매핑 명세를 작성합니다. 아래 새 대상은 매핑 검토의 방향이며, 현재 `import-legacy`가 자동 생성하는 대상이 아닙니다.

| 자산 | 최소 보존 내용 | 새 구조 반영과 검증 조건 |
| --- | --- | --- |
| 원문·첨부·판본 | 원본 바이트와 해시, 원래 ID·경로·URL, 미디어 형식, 판본, 소유자·접근 범위, 철회 상태 | `documents`·`document_revisions`와 원본 저장소로 매핑합니다. 원문을 찾지 못하면 누락을 표시하고 승인·검색 가능한 문헌으로 추정하지 않습니다. |
| 구간·인용 위치 | 원래 구간, 문서 판본, 인용문, 페이지·절·오프셋 등 위치, 파서 버전 | 새 구간화가 필요하면 구간 ID를 새로 만들고 원문 판본 연결을 유지합니다. 위치 형식 불일치와 의미 오류를 같은 오류로 취급하지 않습니다. |
| 개념·용어·별칭 | 원래 ID, 이름·언어·별칭, 설명, 수정자·시각, 근거 | `ontology_concepts`로 매핑할 때 이름 유사도만으로 서로 다른 공정·제품·조건을 합치지 않습니다. 수정 이력은 archive에 남깁니다. |
| 관계·공정 순서·대안 | 양 끝 ID, 방향, 유형, 조건, 근거 판본·구간, 추출·수정 상태 | `ontology_relations`의 방향과 조건을 확인합니다. 벡터 유사도로 상하위·선후행을 새로 만들지 않습니다. 자동 추출과 문헌 승인, 의미 검증 상태를 구분합니다. |
| 출처·출처별 설명 | 게시자·저자·귀속 주체의 원래 값, URL·문헌일, 측면·조건, 인용·근거, 메타데이터 변경 이력 | `publisher`·`author`·`attributed_to`를 구분합니다. 출처별 설명은 현재 승인 문헌과 메타데이터를 확인해 재추출하거나 검증합니다. 과거 요약 문장을 근거 없는 기관 입장으로 승격하지 않습니다. |
| 전문가 수정 | 수정 전후 값, 수정자·시각·이유, 대상 ID·판본, 조건·단위 | 현재 설명에 반영할 수정과 역사 기록을 구분하되 양쪽을 보존합니다. 새 추출 결과로 기존 수정 이력을 덮어쓰지 않습니다. |
| 검토·승인·반려·감사 | 원래 상태명, 대상 판본, 검토자·시각·의견, 작업 중 초안, 변경 지시·감사 이벤트 | 원래 내역은 archive에 보존합니다. 새 공용 검토는 문헌 판본 단위입니다. 과거 위키·주장 승인 상태를 새 문헌 승인으로 자동 변환하지 않으며 주장별 승인 UI를 복원하지 않습니다. |
| 사용자·대화·개인 지식 | 원래 사용자 ID·소유권, 대화·메시지·조건·첨부·인용, 수정·삭제·제외 이력 | 실제 계정과 소유자를 매칭한 뒤 개인 범위로 옮깁니다. 사용자 전체 대화나 개인 위키를 공용 지식으로 반입하지 않습니다. 비밀번호·토큰을 새 인증 방식에 그대로 복사하지 않습니다. |
| 임베딩·검색 기록 | 모델·정확한 차원·변환·입력 해시·접근 범위, 구간 연결, 기존 검색 조건 | 입력·profile·scope가 일치할 때만 재사용합니다. 벡터가 없다는 이유로 원문을 폐기하지 않습니다. 검증하지 못한 벡터는 별도로 보관하고 재색인 대상으로 표시합니다. |

행 수 합계만 같다고 보존이 끝나는 것은 아닙니다. 테이블별 행 수와 판본 수, 주요 원문 해시, ID 매핑의 고아 참조, 수정·검토 이력의 시간 순서, 개인정보·비공개 자료 접근 범위를 함께 확인해야 합니다.

## 5. 고정 평가 자료·기존 벡터 캐시 반입

평가 자료 반입은 운영 이전 도구와 분리되어 있습니다. 구현은 `backend/knowledge/migration/evaluation.py`이며 `--approve-for-development`가 필요하고 DB명이 `_dev` 또는 `_test`로 끝나야 합니다. 이름 검사만으로 운영 서버가 아님을 입증하지 않으므로 연결 대상 확인을 생략하지 않습니다.

```bash
python -m knowledge.cli import-evaluation --corpus-zip /path/to/corpus.zip --evaluation-dir /path/to/evaluation --owner EXISTING_DEV_USERNAME --model text-embedding-3-large --approve-for-development
```

`--owner`는 이미 만든 개발 계정의 사용자명이며 내부 사용자 ID가 아닙니다. 고정 ZIP·구간 목록·메뉴 제외 목록의 SHA-256, 캐시 ID 순서와 차원, 유한한 벡터와 0이 아닌 길이, 구간의 실제 임베딩 입력 해시를 확인합니다. 원문 바이트와 고정 구간·위치를 유지하며, 반입 명령은 임베딩·생성 API를 호출하지 않습니다. 개발용 승인 기록에는 운영 승인·전문가 검증·출처 진위 인증이 아니라는 이유를 남깁니다.

현재 개발 반입 대상은 129문헌, 1,088구간 중 메뉴 등 282구간을 검색에서 제외한 806구간입니다. 제외 구간도 삭제하지 않고 제외 이유를 보존합니다. 제공된 메타데이터의 기관 귀속이 사실인지 이 반입 단계에서 새로 검증했다고 표시하지 않습니다.

| 모델·변환 | 저장 profile |
| --- | --- |
| `text-embedding-3-large`: 기존 API 3,072차원 벡터 앞 1,536차원을 취하고 L2 정규화 | `openai:text-embedding-3-large:api3072:stored1536:prefix_l2:v1` |
| `text-embedding-3-small`: 기존 1,536차원 벡터 사용 | `openai:text-embedding-3-small:api1536:stored1536:native:v1` |

같은 문헌·구간에 두 profile의 연결을 보관할 수 있지만 **한 검색 요청은 지정한 profile 하나로 수행합니다.** 서로 다른 모델이나 변환의 벡터를 한 유사도 공간으로 합치지 않습니다. API에 직접 `dimensions=1536`을 보낸 결과와 과거 3,072차원 캐시의 절단 결과가 동일하다고 이 기록만으로 주장하지 않습니다.

반복 반입 시 동일 profile의 기존 연결을 재사용합니다. 다른 profile의 누락 연결을 추가할 때도 고정 원문 판본과 입력 해시를 먼저 확인합니다. 기존 문헌이 새 판본으로 바뀌었거나 입력이 달라졌다면 중단하며, 현재 원문·승인 상태·활성 색인 포인터를 고정 평가 자료로 덮어쓰지 않습니다.

정확한 cosine 저장·검색 대조는 다음 스크립트로 수행합니다.

```bash
PYTHONPATH=backend python scripts/v2/verify_pgvector_cache.py --evaluation-dir /path/to/evaluation --model text-embedding-3-large --output /path/to/pgvector-cache.json
```

이 명령은 저장소 루트에서 실행합니다. `docs/verification/pgvector-cache.json`에는 기존 28개 질의 벡터로 806개 검색 대상의 top-10을 비교한 통과 기록이 있습니다. 허용 오차는 `1e-5`, 관측한 최대 cosine 거리 차이는 `1.8492246212087338e-7`이며, API 호출은 0회입니다. 동점은 허용 오차 내의 상위 경계로 판정합니다. 이는 NumPy 캐시와 PostgreSQL의 저장·거리 계산·상위 결과 범위를 확인한 것이며, 독립 정답 평가·생성 품질·운영 권한 전체 흐름 검증을 대체하지 않습니다.

## 6. 운영 자료를 받았을 때의 전환 절차

현재 단계에서 아래 작업을 수행했다고 표시하지 않습니다. 실제 운영 자료와 담당자를 확인한 뒤, 별도 환경에서 먼저 실행하고 결과를 검토합니다.

### 6.1 원본 확보와 이전 대장

1. 실제 DB 종류·버전·인스턴스·테이블 목록과 원문 파일 저장소를 확인합니다. 제공된 seed나 평가용 129문헌이 운영 DB를 대표한다고 가정하지 않습니다.
2. 같은 기준 시점의 읽기 전용 DB snapshot/export와 원문 파일 묶음을 확보합니다. 자료가 계속 수정되는 경우 export의 기준 시각과 이후 증분을 구분할 수 있는 식별자를 기록합니다.
3. 원본 export와 각 원문 파일의 크기·SHA-256, 테이블별 행 수·판본 수, 원래 경로와 보관 위치를 이전 대장에 남깁니다. 누락·읽기 실패·중복·참조 불일치를 별도로 표시합니다.
4. 기존 사용자와 새 계정, 소유권·비공개 범위, 검토관과 관리자의 역할을 대조합니다. 확인되지 않은 접근 범위를 공용으로 올리지 않습니다. 검토관을 시스템 관리자만으로 축소하지 않습니다.
5. 보존용 원본과 DB 백업의 접근권한·보관기간·복구 위치를 정하고 실제 별도 환경에서 복구해 봅니다. 파일 저장소와 DB를 같은 기준 시점으로 복원할 수 있어야 합니다.

### 6.2 보존·매핑·검색 준비

1. 새 DB에 버전별 마이그레이션을 적용하고, `import-legacy` dry run의 건수·구조 오류를 원본 대장과 대조합니다.
2. 보관 반입 후 export 해시와 원본 파일 바이트를 재확인합니다. 전체 행 수와 수정 판본 수, 전문가 수정·검토·감사 표본의 모든 필드를 비교합니다.
3. `legacy_mappings`의 각 원래 `(시스템, 테이블, ID)`에 새 대상 또는 명시적인 보관 전용 사유를 정합니다. 관계의 양 끝, 출처 연결, 검토 대상 판본, 사용자 소유권에 고아 참조가 없어야 합니다. 임의의 동일 이름 병합은 하지 않습니다.
4. 새 활성 도메인으로 옮기는 변환은 해당 매핑과 현재 시스템 규칙을 따르는 별도 작업으로 검증합니다. 현재 보관 명령의 성공만으로 이 단계가 실행된 것은 아닙니다. 미해결 매핑과 원문 누락 건수는 0으로 꾸미지 않고 공개합니다.
5. 원문·메타데이터·문헌 판본의 검토 상태를 확인합니다. 공용 검색에는 현재 승인·권한·철회 조건을 충족하는 자료만 반영합니다. 개인 자료·대화·개인 위키는 소유자 범위를 유지합니다.
6. 구간과 입력 해시가 변하지 않은 캐시는 동일 profile·scope에서 재사용합니다. 나머지만 색인 작업에 넣고, 일일 증분 처리와 관리자 즉시 처리의 같은 경로를 사용합니다. 늦게 완료된 작업도 저장 직전 현재 판본·승인·철회·권한을 재확인해야 합니다.
7. 개념·관계·출처별 설명의 근거 연결을 대조합니다. 기관 귀속 메타데이터가 바뀌면 이전 파생 설명을 현행에서 제외하고 재추출하며 과거 기록을 남깁니다. 문헌 승인과 관계의 의미 검증은 다른 상태입니다.

### 6.3 전환 판정·구형 시스템 종료

1. 대표 작업을 새 환경에서 끝까지 확인합니다. 위키 답변 → 관계 카드 펼침·명시적 후속 질문 → 분석 답변 → 외부 문헌 선택 후 원 대화 복귀 → 출처 원문 → 대화 복원 → 개인 위키 정리를 포함합니다. 토글·카드 펼침으로 모델이 호출되지 않는지도 확인합니다.
2. 사용자·검토관·관리자·서비스 계정별 허용/거절, 승인 전·철회 후 자료, 타인 개인 자료, 옛 답변과 개인 위키의 현재 권한 재검사를 검증합니다. 단순히 과거 인용 ID가 있다는 이유로 권한이 사라진 내용을 다시 노출하면 안 됩니다.
3. 검색 누락, 문맥 구성, 관계 해석, 답변 생성의 실패를 분리해 평가합니다. 출처 추적 가능성과 의미 정확성도 분리합니다. 실제 스트림·취소·실패·재시도·사용량 및 `null` 비용 상태를 확인합니다.
4. 데이터 대조 결과, 미해결 예외, 기능 검증, 계정 매핑, 복구 연습 결과를 검토한 뒤 전환 시점·담당자·허용 중단 시간·되돌릴 조건을 정합니다. 현재 구현 작업에는 운영 전환 승인이 포함되지 않습니다.
5. 승인된 전환 시점에 필요한 짧은 쓰기 중지 또는 마지막 증분 export를 적용하고 마지막 수정·삭제·철회 내역을 대조한 뒤 새 서비스로 트래픽을 전환합니다. 장기간 양쪽 DB에 동시에 쓰는 구조를 기본 계획으로 두지 않습니다.
6. 되돌릴 때 새 서비스에서 이미 발생한 작성·검토·삭제 내역을 별도 보존합니다. 새 쓰기를 버리면서 옛 DB만 복원하지 않습니다. 원본 파일·DB·매핑·색인 profile을 함께 복구하고 변경 내역을 대조합니다.
7. 전환 검증 후 구형 실행 경로와 운영 연결을 종료합니다. 과거 코드 복구 지점과 데이터 보관소는 남기되, 옛 탭·호환 서버를 영구 운영하지 않습니다. 보존 데이터 폐기는 코드 삭제와 별도 판단입니다.

## 7. 제거한 실행 코드와 보존 자산

이 구현 브랜치에서 다음 구형 실행 경로를 제거했습니다. 기준 구현은 Git의 위 기준 커밋으로 확인할 수 있습니다.

- `backend/app/`의 이전 서버 진입점, API·서비스·저장소·모델과 탭별 실행 흐름.
- `backend/seeds/seed_runner.py`, `backend/seeds/source_parser.py`의 구형 실행 도구.
- 기존 위키·비교·챗봇·문헌 조사·검토 편집기·구형 seed/import 동작에 묶인 루트 `scripts/`의 실행·검증 스크립트. 새 개발·검증 도구는 `scripts/v2/`를 사용합니다.
- 과거 설계 문서 14개는 삭제 대신 `docs/legacy/`로 이동했습니다. 이 문서의 과거 제약을 새 구현의 실행 기준으로 사용하지 않습니다.

다음은 데이터 자산으로 보존했습니다.

- `backend/seeds/offline_sources_20261023/`의 기존 원문과 데이터 파일, `extracted_concepts.json` 등 JSON.
- `backend/seeds/golden_dataset.py`, `extended_concepts.py`의 리터럴 데이터. 새 서버가 자동 실행하여 승인 지식으로 반입하지 않습니다.
- `backend/app/services/source_extraction_examples.json`의 바이트를 `backend/seeds/source_extraction_examples.legacy.json`으로 옮겨 보존했습니다. 기존 실행 폴더의 경로는 제거했습니다.
- Git의 기준 커밋, `docs/legacy/`의 과거 설계·검증 기록.

파일명이나 과거 필드의 `golden`, `verified`, `adopted` 표현은 원래 데이터의 표기입니다. 새 제품에서 검증된 정답·현재 승인·전문가 인증으로 읽지 않습니다. 기존 운영용 `docker-compose`는 이 구현 단계에서 변경하지 않았으며, 그대로 새 제품을 운영할 수 있다고 주장하지 않습니다.

## 8. 검증 기록과 남은 한계

`backend/tests/test_legacy_migration.py`의 **32개 테스트**를 실제 격리 PostgreSQL 임시 스키마에서 실행하여 통과했습니다. 고정된 개발 `public` 스키마나 운영 DB를 테스트 데이터로 사용하지 않았습니다.

검증한 내용은 다음과 같습니다.

- dry run의 DB·파일 무변경, 원본 export 바이트와 해시, 행·명세·대기 매핑 보존.
- 소스·개념·방향/조건 관계·인용·전문가 수정·검토 초안·감사 기록의 합성 예제 보존.
- 반복 반입, 키 순서 변경, 수정 판본 추가, 이전 export에서 사라진 행 유지, 기존 매핑 보존, 테이블/시스템별 ID 분리.
- 정밀한 JSON 숫자를 PostgreSQL 숫자로 보존하고, 문자열·불리언과 구분하는 검사.
- 잘못된 ID·JSON·시스템명 거절, DB 중간 실패 시 명세·행·매핑의 전체 롤백.
- 비공개 레거시 반입 후 공용 문헌·개념·관계·승인·작업이 생성되지 않고 일반 사용자와 검토관의 문헌 검색에도 나타나지 않는 검사.
- 실제 `002_legacy_imports.sql`을 이전 형태의 임시 스키마에 적용했을 때 기존 payload 보존, 원본 불명 행의 `first_import_id = NULL`, 재적용 생략, 적용 SQL 변경 차단.
- 합성 캐시 자료를 이용한 개발용 반입 제한, 원문·판본·승인 보존, 반복 반입, large/small profile별 누락 벡터 연결 추가와 검색 분리. 이는 실제 129문헌의 의미 평가가 아닙니다.

별도의 실제 평가 캐시 저장·검색 대조 결과는 앞서 설명한 `docs/verification/pgvector-cache.json`에 있습니다. 이 두 검증을 운영 이전 완료나 전문가 지식 검증으로 합쳐 표현하지 않습니다.

아직 확인하지 못한 것은 실제 운영 테이블 전체, 원문 파일의 완전성, 소유자·역할 매핑, 전문가 수정·검토 이력의 실제 분포, 운영 데이터의 활성 도메인 변환 결과, 운영 환경에서의 복구·전환입니다. 해당 자료가 들어오면 이 문서의 이전 대장과 미해결 목록을 실제 값으로 채우고 필요한 변환을 별도 마이그레이션으로 구현해야 합니다.
