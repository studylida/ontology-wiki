## Existing chat boundary: Stages 1–5 (fixture integration, not production qualification)

`knowledge.main` now composes Identity, Conversations, Documents, Answers and the manual Wiki service. Existing chat migrations are `001_foundation.sql`, `002_documents.sql`, `003_answers.sql`; the wiki adds `004_shared_wiki.sql` and `005_wiki_discovery.sql`. Never rewrite applied migrations. Stage 4 connects the React frontend to these contracts; Stage 5 integrates regression tests, synthetic evaluation and fresh Compose smoke checks. Neither adds a schema. The root HTML/JS prototype and retired frontend hooks, screens and contracts are removed. Run the UI from `frontend`.

The API requires one process per DB (`--workers 1`), enforced by a dedicated PostgreSQL session advisory lock. This prevents startup recovery from interrupting another live API's generation. Concurrent conversations are asynchronous within that process. The document worker is separate and uses its own lock. Do not silently remove these locks or claim multi-replica operation is implemented.

Startup checks the schema and records abandoned answer runs as interrupted. It does not migrate, create users, invoke a provider or start document processing. GET/reconnect never generates another answer. `POST /conversations/{id}/messages` saves only; the UI uses `/conversations/{id}/turns` for an actual question, not both.

## Shared wiki stage 1 boundary

`knowledge.wiki` and additive `004_shared_wiki.sql` provide employee page creation/title search/read/edit/history/diff/restore and admin protection. `wiki/policy.py` owns read/edit/protection predicates and `baseVersion` checks, using shared principal checks in `identity/authorization.py`. `WikiService` uses the same policy for mutations and advertised UI capabilities and owns idempotent orchestration; `WikiRepository` owns SQL/row locks/revisions/receipts. Do not copy Documents' uploader-only management policy: all employees edit ordinary wiki pages. Admin alone changes protection or edits/restores a protected page. Revert creates a new content revision and never restores old protection settings. Titles are not identity and need not be unique.

The page `version` includes protection changes; content `revisionNumber` does not. Every mutation locks the actor/request key then the page row and commits page/revision/receipt together. Same-request replay acknowledges an existing receipt without a new write; different payload is a conflict. Preserve stale drafts and require explicit latest-version review instead of automatic merge. No provider or worker is required for manual wiki operations. Do not change applied `001~007` SQL in later phases.

The frontend wiki uses View/Controller/Service/Repository/DTO; shared authenticated HTTP and safe Markdown remain single owners. Current, preview and historical Markdown all use the same safety policy. The wiki view stays mounted after first entry to preserve an in-memory draft across tabs, but is cleared on logout. Unsent drafts are memory-only with unload warnings. Only submitted wiki commands and confirmed receipts are kept in user-scoped sessionStorage for explicit same-tab refresh recovery; logout clears them. A confirmed write followed by a failed read must retain its receipt and retry GET only, never write again. Unknown delivery resends the identical request ID/payload only on explicit user action. Read/history failures from an obsolete selection must not change a newer page. Conflict recovery also covers restore/protection outside the editor. The source/business-context note is optional staff-authored text, not verified citation metadata.

Wiki stage 2 adds stable `/wiki/wpg_<hex>` stored Markdown navigation, aliases/meaning and exact-name ambiguity hints. `wiki/search.py` owns bounded search/similarity/retry use cases; repositories own SQL; policy remains the sole read/edit/version gate. DTOs describe actual source revisions. Name candidates remain visible while indexing is pending, but body results must be current AND indexed. Never substitute obsolete text while labelling it current. Stage 3 below adds wiki chat evidence and authenticated Markdown export. Unapplied AI proposals remain excluded from those public paths.

`wiki/indexing.py` reuses source-preserving segmentation and the small IndexUnit contract; `indexing/embeddings.py` and `indexing/repository.py` own provider batch validation/cache for both sources and wiki. One existing worker processes both queues fairly with short transactions and current-revision rechecks around provider I/O. No model calls on page read. Editing enqueues one job per revision atomically; old pending jobs are superseded. Failed jobs can be retried without duplicating passages/vectors. Profile mismatch requires explicit reindex; do not mix fixture/live vectors. Optional rerank and lexical scoring helpers are shared in `rag/ranking.py` without changing chat evidence selection.

Frontend `wikiNavigation` owns URL/history I/O; `wikiLinks` owns canonical internal path validation. Arbitrary relative paths are NOT an allowed URL policy. Discovery Controller owns cancelled reads/status polling/explicit search; Service owns labels and use cases; Repository owns HTTP. Similarity checking never blocks saving and never persists a private draft. No per-keystroke embedding or read-time generation. Existing edit/receipt recovery stays intact.

Tests include `tests/foundation/test_wiki_discovery.py`, `tests/browser/test_wiki_discovery.py` plus existing wiki/chat regressions. Browser CI stays on Ubuntu 24.04. A local `OW_TEST_CHROMIUM_EXECUTABLE` may select an installed browser; leave unset in CI for its pinned Playwright browser. A browser-policy block is an unexecuted browser test, not a product pass.


## Shared wiki stage 3 boundary

Additive `006_wiki_publication.sql` adds withdrawal, independent of edit protection. RAG merges actual indexed current wiki passages with active document passages before the existing optional reranker, context budget and CitationNormalizer. Name-only wiki hits are not evidence. `wiki/evidence.py` owns wiki evidence SQL; `evidence/access.py` composes existing document rules and wiki readability/currentness for retrieval, generation completion, history and SSE. Existing server revision namespaces identify kinds; unknown IDs fail closed. Do not bypass document withdrawal or private-conversation ownership.

Wiki citations have `sourceKind=wiki`, `pageId`, real revision and passage IDs, never a fabricated documentId. Document citations retain their real document identity. Revision replacement keeps historical citations readable but excludes old assistant content from current follow-up context. Admin withdrawal removes the wiki from read/search/export, cancels pending indexing and hides dependent stored answers. Replay acknowledges a recorded write without another mutation. Source reads take a short DB snapshot, not a provider call under a lock.

`GET /wiki/pages/{id}/markdown?revisionId=...` returns exact stored UTF-8 Markdown with attachment/nosniff and identity/hash headers; the Link header points to existing revision JSON metadata. `GET /wiki/pages/{id}/passages` provides actual quoted sections. Both reuse employee authentication. `POST /wiki/pages/{id}/deactivate` uses the same admin/version/idempotency boundary. There is no public anonymous export or new external integration service.

Frontend `sourceService` validates actual source kind/revision/passage; `sourceRepository` dispatches authenticated HTTP/download. The existing source controller/panel and citation numbering serve both kinds. Wiki source notes are staff-authored context, not verified citation metadata. Do not invent a document FK from a note, claim independent corroboration from a wiki paraphrase, or copy personal conversations into public knowledge. Unsaved similarity inputs do not become published evidence. Future proposals must remain outside public retrieval/export until explicitly applied.

The stage-3 tests use real storage/HTTP and fixture generation/embedding. Injected reranker tests check one mixed-source call, not CrossEncoder quality. Live-model evaluation and employee usefulness remain unverified unless separately run with approved credentials/data/budget. Read-only wiki/export/history does not invoke models.

## Shared wiki stage 4 — requested AI proposals

Additive `007_wiki_proposals.sql` stores private proposals separately from pages/passages and records reviewed AI provenance on published revisions. `wiki/proposals` separates request/apply services, SQL/queue, bounded generation and pure minimal-change checks. The existing worker handles requested generation as a serial queue. Stage 5 adds separately enabled document-origin discovery below. API startup and GET never call a generator. Interrupted work becomes failed; regeneration needs an explicit new request.

Only the requester and (for a targeted page) an administrator may inspect a manually requested or chat-selection proposal. Stage 5 document-origin proposals use the separate shared-source scope below. A protected-page proposal is allowed, but publication uses `WikiService.write` with current `wiki/policy.py` permissions and the stored base version. No new editor authorization rules. Publication locks request/receipt, proposal and mixed sources in a fixed order; page, revision, provenance, proposal state and receipt commit together. Stale sources/target revisions are not silently merged. Same request replay acknowledges existing work without new writes or model calls.

Chat selection uses existing conversation ownership and visible-message policy. Only an explicitly selected contiguous excerpt enters the private proposal. Whole conversations/nonselected text and conversation identifiers are not published in provenance. The human reviews the final Markdown and source note before publication. Employee experience needs no invented document citation. AI provenance records consulted evidence, not semantic certification; restoring a revision preserves that provenance.

Generation uses the existing provider and mixed RAG without creating a fake private conversation/retrieval run (`record=False`); trace and usage stay with the proposal. Link candidates combine existing hybrid similarity search with title/alias mentions, then one structured model response judges contextual identity and usefulness. Mechanical checks preserve untouched prose, reject ambiguous/overlapping edits and skip dubious/repeated/code links. These checks are not proof of semantic correctness. Fixture mode returns explicitly labelled contract output; link quality/live evaluation remains separate.

Frontend proposals preserve View/Controller/Service/Repository/DTO responsibilities. HTTP, safe Markdown, source panel and user-scoped submitted-command recovery are reused. A known POST receipt followed by failed GET retries GET only; no automatic POST on reload. No general draft autosave/expiry/assignment/moderation system. Requested generation is bounded by `OW_WIKI_PROPOSAL_TIMEOUT_SECONDS` (default120, max300), current page20000 chars, evidence12000 chars, output45000 chars; no provider calls under DB locks. Manual editing and normal chat do not depend on proposal success.

## Single-owner responsibilities

- Documents owns shared visibility, active revisions and raw integrity. Upload/read is open to employees; updates/reprocess/deactivation require uploader or admin. Deactivation is not undone by a worker. The UI uses `canManage`, not a second role/approval policy.
- Preprocessing preserves structure, source offsets and held passages. `integrations/document_parser.py` separates conversion from URL fetching. Keep existing Markdown/PDF/JATS assets.
- Indexing owns the small IndexUnit contract, reusable vectors and atomic activation; Jobs owns execution/retry. A failed new revision keeps the earlier valid active revision. Reprocess retries failed jobs, not force-reextracting ready revisions.
- DocumentRepository owns active-source retrieval SQL. RAG owns candidate selection, optional reranking, source-provided companions, neighbors and whole-passage context budgeting. No ontology dependency or Extended branch.
- Answers owns question policy, run idempotency, cancellation/retry and commit-before-publication events. `answers/prompt.py` owns generation policy; `answers/citations.py` owns normalization/numbering. A citation ID check is not semantic entailment validation.
- `evidence/access.py` composes source readability and currentness; `conversations/protection.py` is the shared stored-answer/history presentation policy. Withdrawal hides dependent answer content/citations and prevents replay. Replaced but readable revisions are labelled historical; their old assistant messages are not reused as current context.
- Frontend repositories own HTTP, authenticated SSE, source downloads and sessionStorage. Services own event application/reconnection and the canonical citation map. Controllers own lifecycle, cancellation and state. Views render actual server states, not invented progress or success. DTOs contain current contracts only.
- Existing provider adapters remain explicit. Never silently replace a failed live model with a fixture. No paid calls without approved account/data/budget scope.

The live runtime registry contains only current task/cancellation state. PostgreSQL holds messages, runs, retrieval diagnostics and ordered event batches. Commit the body/state/events together before exposing complete. Storage errors are not successful answers. Read run body and durable cursor under the same short DB lock; do not hold that lock during provider/SSE I/O. Reconnect resumes after the durable sequence; retry requires a new requestId and reuses the original user message. Same-user same-request replays return one run. Changed payloads conflict.

The browser replaces a restored body and cursor together before replaying newer events. EOF is not completion. Only explicit send/retry submits POST. Unknown POST delivery retains the original requestId for explicit resend; never invent a new ID for transport recovery. Session storage is user-scoped and does not cache answers or migrate retired drafts. Logout clears the current workspace. Body footnotes, source list and source panel use the server's numbers through `services/citationService.ts`. Markdown HTML/images are not executable/rendered; unknown IDs do not become clickable citations.

## Architecture and work boundaries

Backend: Controller / Service / Repository / Entity / DTO. Frontend: View / Controller / Service / Repository / DTO. These are responsibility boundaries, not mandatory empty forwarding classes. Organize by capability; avoid duplicate rules and a giant utils/service module.

Keep the modular monolith, PostgreSQL/pgvector and existing provider interfaces. Do not add brokers, graph databases, agent frameworks, speculative extracted-knowledge tables or approval workflows. Fail closed for unauthorized/corrupt sources and fail soft for independent valid evidence and optional refinements. General knowledge may supplement explanations but cannot invent internal facts.

Use isolated dev/test databases. No destructive production/shared DB or raw-volume operations, no secret commits, no force push, main merge or deployment. Old personal-wiki rows need no migration, but Git history does not back up raw files or DB rows. Maintain two independent architecture sources: docs/CHAT_ARCHITECTURE.md and docs/WIKI_ARCHITECTURE.md. Do not add per-run reports or sensitive dumps.


## Shared Wiki Stage 5: opt-in document-origin discovery

`008_wiki_document_proposals.sql` is additive; never rewrite `001~007`. `wiki/automation` owns the durable revision-keyed discovery queue, source/candidate comparison, limits and read-only notice. Existing document indexing is not its approval gate: completion of usable indexing permits discovery, and discovery failure never changes source index state. The serial worker reconciles eligible revisions on each work iteration, rotates queue types and recovers interrupted discovery as failed without paid auto retry. No model calls or queue creation on GET. Wiki edits only enqueue wiki indexing, not document discovery.

Automatic use is explicitly disabled by default (`OW_WIKI_AUTO_PROPOSALS_ENABLED=false`) to prevent unapproved live costs. Enable consistently on API/worker. Default reservations: 20 source revisions/day UTC, at most 2 proposals each. Reservations survive restarts, including failed attempts. Existing timeout/character bounds apply. This is a call/work bound, not a precise currency cap. No old-corpus backfill: source revisions must be created at/after migration 008's applied_at. Replacing a document creates an eligible new revision; reprocessing/reloading does not create another discovery for that revision.

Only the internal enqueue entry accepts an origin revision and concrete source passage IDs. User request DTOs must reject origin injection. Automatic discovery pins real usable source passages, obtains existing wiki candidates through existing hybrid retrieval and may choose no changes. Same name is not semantic identity. Source-invalid or ambiguous ideas are skipped; automatic edits with no actual change are not queued for mandatory review. Do not present fixture copying as intelligent summarization.

`ProposalService` remains the single application path for requested and automatic proposals. Document-origin proposals are employee-shared; private employee/chat requests stay owner/admin scoped. Current/withdrawn source checks apply to reading and applying shared suggestions. Published revisions record real source provenance, not invented employee testimony. Unapplied suggestions are not indexed or exported. Preserve common auth, wiki policy, optimistic versions, idempotency and original locked-document behavior.

The document notice uses View/Controller/Service/Repository/DTO and the existing `WikiProposals` review UI. Browser polling is GET-only, abortable and nonoverlapping; it cannot resubmit paid work or reset human review edits. Document upload/read remain usable when the optional notice fails. No separate approval dashboard, automatic publication, outside web watcher or new queue framework.

Tests: foundation/test_wiki_automation.py and browser/test_wiki_automation.py alongside existing regression. Browser fixture param enables auto proposals only for these tests. Fixture orchestration is not model-quality or employee-usefulness validation. The source owner must still be an active employee; automation never fabricates a privileged principal.
